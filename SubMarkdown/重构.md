### 第一，划分职责

前面提到，传递函数指针或者某个实例给依赖，依赖是不需要知道你给他传递什么的，它只需要关心你注入的依赖是否正确，能够满足自身的需求。所以这里我们需要面向接口编程，接口相当于给外界定的契约，但需要遵守一个原则——接口隔离。比如说之前给点这个类注入LFOPointManager，它只接收LFOPointManager这一个类型，这超出了点这个类的职责。因此我们需要给LFOPointManager实现接口，但只是一个接口吗？很显然这解耦的作用比较弱，这里的解耦是给调用端的，LFOPointManager里面有很多函数，但你不能保证点这个类一定需要这些函数。这就是为什么需要接口隔离原则，按照职责划分接口。因此这里修改LFOPointView和LFOCurveView的构造函数的签名

这就很清楚地向外界表明自己的需求，写代码的时候就不容易犯错

PaddedLFOPointManager.h

```cpp
#pragma once

#include <stdexcept>
#include <vector>

#include "LFOPointManager.h"

template <typename T>
class PaddedLFOPointManager : public LFOPointManager<T>
{
public:
	using Base = LFOPointManager<T>;

	explicit PaddedLFOPointManager(T width, T height, T padding)
		: Base(checkedInner(width, padding),
			checkedInner(height, padding))
		, width_(width)
		, height_(height)
		, padding_(padding)
	{
		syncCache();
	}

	int addPoint(const LFOPoint<T>& point) override
	{
		const LFOPoint<T> internalPoint{
			point.x - padding_,
			point.y - padding_
		};

		const int ret = Base::addPoint(internalPoint);
		syncCache();
		return ret;
	}

	int deletePoint(int pointIndex) override
	{
		const int ret = Base::deletePoint(pointIndex);
		syncCache();
		return ret;
	}

	const LFOPoint<T> originPoint() const noexcept override
	{
		return LFOPoint<T>{T(padding_), T(padding_)};
	}

	const std::vector<LFOPoint<T>>& points() const noexcept override
	{
		return externalPoints_;
	}

	const std::vector<LFOPoint<T>>& controlPoints() const noexcept override
	{
		return externalControlPoints_;
	}

	const T drawPointWidthRange() const noexcept override
	{
		return width_ - padding_;
	}

	const T drawPointHeightRange() const noexcept override
	{
		return height_ - padding_;
	}

	int movePoints(int pointIndex, T x, T y) override
	{
		const int ret = Base::movePoints(
			pointIndex,
			x - padding_,
			y - padding_);

		syncCache();
		return ret;
	}

	int moveControlPoints(int pointIndex, T x, T y) override
	{
		const int ret = Base::moveControlPoints(
			pointIndex,
			x - padding_,
			y - padding_);

		syncCache();
		return ret;
	}

	int moveEndPoints(T y) override
	{
		const int ret = Base::moveEndPoints(y - padding_);
		syncCache();
		return ret;
	}

	int reset() override
	{
		const int ret = Base::reset();
		syncCache();
		return ret;
	}

private:
	T width_;
	T height_;
	T padding_;
	std::vector<LFOPoint<T>> externalPoints_;
	std::vector<LFOPoint<T>> externalControlPoints_;

	static T checkedInner(T outer, T padding)
	{
		if (padding < T(0))
		{
			throw std::invalid_argument("padding must be >= 0");
		}
		if (outer <= T(2) * padding)
		{
			throw std::out_of_range("outer size must be > 2 * padding");
		}
		return outer - T(2) * padding;
	}

	void syncCache()
	{
		const auto& internalPoints = Base::points();
		const auto& internalControlPoints = Base::controlPoints();

		externalPoints_.clear();
		externalPoints_.reserve(internalPoints.size());
		for (const auto& p : internalPoints)
		{
			externalPoints_.push_back(LFOPoint<T>{
				p.x + padding_,
					p.y + padding_
			});
		}

		externalControlPoints_.clear();
		externalControlPoints_.reserve(internalControlPoints.size());
		for (const auto& p : internalControlPoints)
		{
			externalControlPoints_.push_back(LFOPoint<T>{
				p.x + padding_,
					p.y + padding_
			});
		}
	}
};
```

### 第二，让逻辑变得更纯粹

这个其实和上面的职责分离很相似，似乎更侧重于如何分离？其实在之前LFO的绘制里可以发现，`draw`方法里面写了draw无关的内容。比如LFOCruveView里面的`draw`方法，里面甚至做了Lerp的运算，从纯粹的逻辑角度上来说，这还不够抽象，`draw`应该只负责绘制。也就是说`draw`里面可以从接口获取点或者是什么其它的，至于点为什么会在这里它完全不需要关心

因为LFOCruveView暂时不需要新增什么，所以我先不去重构它省时间，这里用新写的waveform组件展示

发挥想象力设计接口

idrawwaveform.h

```cpp
#pragma once

#include <vector>

namespace yzaudiolib::vstgui::waveform
{
	struct point
	{
		float x;
		float y;
	};

	class IDrawWaveform
	{
	public:
		virtual float originPointX() const noexcept = 0;
		virtual float originPointY() const noexcept = 0;
		virtual float drawWidth() const noexcept = 0;
		virtual float drawHeight() const noexcept = 0;
		virtual const std::vector<point>& drawPoint() const noexcept = 0;
		virtual int numSample() const noexcept = 0;
	};

	class ISetDrawWaveform
	{
	public:
		virtual int setSample(float* sample, size_t begin, size_t end) = 0;
	};

}
```

`ISetDrawWaveform`用于接收端，在实现中就是把采样点拷贝到vector容器中

`IDrawWaveform`就是CView需要用到的接口，它只需要这些方法就能完成波形图的绘制

现在就可以写waveform的绘制方法了

```cpp
void WaveformView::draw(CDrawContext* context)
{
	CGraphicsPath* strokePath = context->createGraphicsPath();
	if (strokePath)
	{
		auto numPoints = iDrawWaveform.numSample();
		strokePath->beginSubpath(iDrawWaveform.drawPoint().at(0).x, iDrawWaveform.drawPoint().at(0).y);
		for (size_t i = 1; i < numPoints; ++i)
		{
			strokePath->addLine(iDrawWaveform.drawPoint().at(i).x, iDrawWaveform.drawPoint().at(i).y);
		}

		context->setFrameColor(CColor(238, 130, 238, 255));
		context->setLineWidth(2.0);
		context->drawGraphicsPath(strokePath, CDrawContext::kPathStroked);
		strokePath->forget();
	}
}
```

其实甚至可以把里面硬编码的颜色和宽也抽象化，不过我懒得这样做了。这真的单纯只是因为我懒，不是过度设计，因为要绘制waveform颜色和宽也不是由它自己决定的。比如说我想要根据音量大小绘制不同颜色的波形，上面的接口代码中已经有了原点和绘制的宽高，所以每一块绘制不同颜色的波形就行了。想要实现不同的功能只需要替换对应的实例，真的超级方便！

这里的waveform定死了60hz，虽然dataexchange的回调`onDataExchangeBlocksReceived`默认是ui线程，理论上可以直接事件驱动。但我还是觉得从controller里拿CView的裸指针不太安全。但是可以在接口中新增方法或者新增接口，添加新的函数，用标志来控制重绘
